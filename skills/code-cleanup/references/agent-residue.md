# agent 残留的分类学

人类留下残留，通常是因为赶时间和偷懒。agent 留下残留，原因不同，因此形态可预测：

| 成因 | 产生的形态 |
| --- | --- |
| 只读到文件的一部分（上下文切分） | 在旧实现旁边新增一份，而不是替换 |
| 倾向"新增"而非"改写/删除" | 双份实现、平行分支、第二套工具函数 |
| 压缩后记忆错位 | 把已删的东西按摘要重建，或引用不存在的符号 |
| 以"让检查通过"为目标 | 类型逃逸、空 catch、默认值兜底 |
| 过度泛化以求稳妥 | 只被调用一次的包装层、抽象接口、配置项 |
| 删除没有"完成感"，新增有 | 旧路径长期滞留，无人回收 |

**所以这一类残留可以按形态检索，而不必猜"这段是不是 AI 写的"。** 判断只针对"它是否还对应仓库现在的真实行为"，不做风格审判。

---

## 1. 双份实现（最危险）

**识别信号**

- 同目录或跨目录存在近同名函数：`getUser` / `fetchUser` / `get_user_by_id`
- 后一份多了一点东西：多了日志、多了一层 try、参数少一个
- 调用点分散在两边，且两边的行为已经在细微处分叉
- `repo_scan.py` 的 `dup_block` 命中；`jscpd` 或 `knip` 报告重复导出
- `git log` 显示两份在相近时间窗内被创建

**为什么最危险**：下一次生成会在这两份之间随机挑一个作为"参考"，污染会自我放大。

**处理**：R2。必须确定哪份是权威实现——依据是调用点数量、测试覆盖、是否有外部引用，而不是"哪份更新"。删除另一份要同步改调用点，属于跨文件改动。

**陷阱**：A/B 两套都活着是设计；旧版为兼容客户端保留是契约。判据是有没有版本协商或 deprecation 声明。

---

## 2. 无谓抽象（needless indirection）

**识别信号**

- 函数体只有一行转发：`def get_user(uid): return repo.find(uid)`
- 只被调用一次，且没有测试单独覆盖它
- 接口只有一个实现，参数与实现完全一致
- 文件名带 `Manager`/`Service`/`Handler`/`Helper`/`Factory`，但实质是薄壳
- "为将来预留"的可选参数，全仓无人传

**处理**：R2。删掉会改调用链（哪怕只是少一跳），且"这个抽象是否值得保留"是设计判断，不是清理判断。

**陷阱**：有些薄壳是有意的接缝（测试替身、依赖注入点、跨模块边界）。判据：有没有测试在这个接缝上替换实现。

---

## 3. 过度防御（defensive overkill）

**识别信号**

- `try { ... } catch { return defaultValue }`，且默认值与失败语义不匹配
- `except: pass` / `catch {}` 空块
- 对刚构造出来的对象判空；对已经校验过的输入再校验一次
- 同一个数据三层 fallback（`a ?? b ?? c ?? ""`）
- 为纯函数包重试/超时
- 注释写"防御性编程"

**为什么难判**：这不是"多余代码"，是**错误处理策略**。删掉会改变失败时的行为——从"静默降级"变成"抛出"，可能让原本能跑的场景崩掉。

**处理**：R2 起步，触到鉴权/支付/数据写入的按 R3。**永远不自动删**。

**陷阱**：它常常是为了让某个测试通过而加的，删掉会红。先看有没有测试锁住这个行为，再看这个行为是不是用户想要的——这属于产品判断，不是清理判断。

---

## 4. 类型与检查逃逸

**识别信号**：`any` / `Any` / `interface{}` / `unknown` 强转 / `@ts-ignore` / `@ts-expect-error` / `# type: ignore` / `eslint-disable` / `nosec` / `as unknown as X`

**处理**：R2。逐个判断是"绕过真问题"还是"绕第三方类型 bug"。

**陷阱**：有些 escape 是唯一可行解（库的类型声明错了、动态键无法表达）。删掉会引入新的类型错误，属于重构而非清理。只报告，附带"为什么这里是必要的"的猜测，让人确认。

**例外**：`@ts-ignore` 下面紧跟的是一行因为该 ignore 才编译通过的代码——这种是隐患而非清理对象，标注为"技术债"而不是"残留"。

---

## 5. 幻觉 API 面

**识别信号**

- 调用了库里不存在的方法、传了不存在的参数、用了不存在的配置键
- `README` 里的命令跑不通，flag 不存在
- 引用的模块路径不存在（`repo_scan.py` 的 `broken_import` 直接命中）
- import 了从未安装的包

**处理**：R1 里最特殊的一类——**它已经坏了**，修它是必须的。但"怎么修"要确认：改成正确的 API，还是删掉这段从未生效的代码？两者语义不同。

**判据**：这段代码有没有可能曾经跑通过（看 git 历史）？从没跑通过 → 大概率是生成时臆造的，删；曾经跑通过 → 库升级导致，改调用。

---

## 6. 僵尸模式与指令漂移

**这是清理工作的核心，也是最容易被跳过的一步。**

**识别信号**

- `AGENTS.md`/`CLAUDE.md`/`README` 描述的文件、模块、命令、目录结构已不存在
- 文档里的示例 import 指向已删路径
- 注释写"见 `xxx.py`"，文件已删
- 文档说"我们使用 X 方案"，代码里是 Y
- CI 配置跑的是已重命名的脚本
- `package.json` 的 `scripts` 指向不存在的文件
- 计划/状态文件（`STATE.md`、`TODO.md`、设计文档）描述的目标已经实现或已放弃

**为什么优先级高**：删掉代码但留着描述，下一个 agent 会照描述把代码写回来。你清掉的东西会以更高成本复活。

**处理**：R2，且**必须写进报告并单独成组**。修改指令文件会改变后续所有 agent 的行为，不能擅自动手。

**报告写法**：

```
删除 `src/pricing/v1.py` 后，以下 3 处描述已失效：
- AGENTS.md:34 「定价逻辑在 src/pricing/v1.py」
- docs/pricing.md:12 示例 import 该模块
- src/checkout.py:8 注释引用该文件
```

## 归属判定：不要做作者识别

不要试图判断"这段是人写的还是 AI 写的"。做不到，也不需要。只需要判断：

1. 它现在还在运行路径上吗？（引用与调用链）
2. 它对应的描述还成立吗？（文档与实现比对）
3. 它和周围代码的约定一致吗？（同一仓库内的写法冲突）

时间窗只能用来**排优先级**（`repo_scan.py --since-days` 给近期改动的文件打 `🆕`），不能用来定性。近期改过的地方更可能有没收尾的残留，仅此而已。

## 反模式：把清理变成风格审判

以下都不算清理，做了就是越界：

| 行为 | 为什么错 |
| --- | --- |
| 删掉注释里的中文/表情/口语化表达 | 与行为无关，纯风格偏好 |
| 把变量名改成"更专业"的写法 | 重命名，R2 起步，且不是清理 |
| 给所有函数加类型标注 | 新增代码，属重构 |
| 把 `any` 全换成具体类型 | 需要设计判断，且会引入编译错误 |
| 删除"看起来是 AI 写的"整个模块 | 没有引用证据，等于凭感觉删 |
| 统一代码风格（缩进、引号、import 顺序） | 格式化，不是清理 |
| 把长函数拆短 | 重构，且改变 diff 可读性 |

判据很简单：**这条改动，能用"它已不对应真实行为"来辩护吗？** 不能，就不属于这个 skill。
