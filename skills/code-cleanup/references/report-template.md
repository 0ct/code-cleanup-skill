# 输出模板

四段，顺序固定（第 2 段内含"度量"小节）。少一段都算没交付。

---

## 第 1 段 · 结论

```
扫描 <N> 个文件（<M> 个代码文件），修复 <X> 项，待确认 <Y> 项，其中 <Z> 项落在近 30 天改动过的文件里（🆕）。
验证：<跑通了什么 / 未验证什么>。
清理效果：死代码 <a>→<b>，未使用依赖 <c>→<d>，过期标记 <e>→<f>。
```

三句话，不超过四行。不要开场白，不要"本次清理遵循了最小改动原则"这类自述。

**必写**：验证到达的程度。跑不了测试就写"未验证：项目无测试"，不要含糊成"已检查"。

**必写**：至少一项可核对的数字变化（来自 `--baseline` 对比）。只说"清理完成"不算交付。

| 3 | `src/api/client.py:88` 🆕 | 过期注释 | 注释由"升序"订正为"降序" | 实现为 `sort(reverse=True)`，测试断言降序 | — |

**硬约束**：

- 每行必须有**能点开的位置**：文件 + 行号或函数名。写不出位置的改动不许列。
- "依据"必须是**可复核的事实**（引用计数、测试结果、工具输出、命令），不是"看起来没用到"。
- 引用了工具结论的，写明工具名；脚本与工具结论一致时标"同结论"，冲突时在清单里说明。
- "验证"列写实际执行结果。没验证写 `已改待验证`，并列在下方。
- 近期改动过的行标 `🆕`——它是"上一轮没收尾"的强信号。

改完待验证的，单列：

```
待验证：<位置> — 建议执行 `<命令>` 确认 <什么>
```

## 第 3 段 · 待确认清单

按优先级分组，组内按文件路径排序。**默认不改，等你确认。**

### P0 — 会造成实际故障

| 位置 | 问题 | 判断依据 | 建议处理 | 潜在风险 |
| --- | --- | --- | --- | --- |
| `src/api/orders.py:120` | 导入了已删除的 `pricing_v1` | 模块文件不存在，`pricing/` 下只有 `v2.py`；运行时将 ImportError | 改为 `from pricing.v2 import calc`，并核对参数是否一致 | v2 的税率参数与 v1 不同，直接替换可能改变计算结果 |
| `package.json` | `next` 声明为 `^14`，代码使用 `next/font` v15 API | 类型检查 3 处报错指向该 API | 升级到 v15 并跑完整构建 | 升级涉及 breaking change，须单独排期，不属于清理范围 |

### P1 — 逻辑矛盾或契约风险

| 位置 | 问题 | 判断依据 | 建议处理 | 潜在风险 |
| --- | --- | --- | --- | --- |
| `config.py:12` / `client.py:40` | `MAX_RETRY` 两处定义不同（3 / 5） | 两个常量同名同义，值不一致 | 确认唯一来源后合并 | 不确定哪个是线上实际生效值，改动会改变重试次数 |
| `docs/api.md:88` vs `src/routes.ts:31` | 文档写默认 `limit=50`，实现是 `20` | 代码与文档冲突 | 确认产品意图后对齐其一 | 改实现影响现有客户端分页行为 |

### P2 — 卫生问题，可排期

| 位置 | 问题 | 判断依据 | 建议处理 | 潜在风险 |
| --- | --- | --- | --- | --- |
| `src/legacy/`（4 个文件） | 疑似无引用目录 | 全仓引用 0，但目录名暗示历史模块 | 确认无外部消费后整目录删除 | 可能有运维脚本或内部工具在 import |
| `.env.example` | `SENTRY_DSN` 无消费方 | 代码只读 `SENTRY_DSN_URL` | 确认部署侧用法后删除或改名 | 部署脚本可能注入该键 |

### 描述失效（本次未删也会出现的"僵尸种子"）

单独成组，因为它们不修，下一次就会把已删的东西写回来。

| 位置 | 描述内容 | 与现状的冲突 | 建议 |
| --- | --- | --- | --- |
| `AGENTS.md:34` | 「定价逻辑在 `src/pricing/v1.py`」 | 该文件已不存在，现为 `pricing/v2.py` | 更新路径，或改为指向 `pricing/` 目录（由人确认意图） |
| `docs/api.md:12` | 示例 `import { calc } from "./pricing/v1"` | 模块不存在 | 更新示例；示例被复制到下游，优先修 |
| `src/checkout.py:8` | 注释「与 v1 保持一致」 | v1 已删，参照物消失 | 删除该注释或改写为当前约束 |

**硬约束**：

- 一行一个可执行动作。写"考虑重构 xxx"是废话，写"`a.py:12` 与 `b.py:40` 两个 `MAX_RETRY` 合并为一个，取值待定"才是条目。
- "判断依据"必须包含**看得见的证据**（路径、行号、命令、计数）。
- "潜在风险"必须写**改错会怎样**，不能写"可能有风险"。
- 拿不准的一律标注置信度：`高 / 中 / 低`，低置信的放 P2 并说明还缺什么证据。
- 涉及 R3 区的条目，在问题列前缀 `[勿自动处理]`。
- 双份实现类的条目，必须写明"建议保留哪一份"及理由（调用点数量 / 测试覆盖 / 外部引用），而不是留给用户选。

## 第 4 段 · 未覆盖范围

```
- 未扫描：`vendor/`（第三方代码，不在清理范围）、`docs/`（仅抽查 2 个文件）
- 未深读：`src/analytics/`（12 个文件，仅看导出面）
- 未验证：无集成测试，`docker compose up` 因缺 `.env` 未能执行
- 未跑工具：`knip` 因依赖离线安装失败，死代码结论仅来自脚本 + 引用计数
- 扫描工具截断：`markers` 达 200 条上限，`src/legacy/` 内可能还有未列出项
- 第二遍复扫：`unused_file` 仍有 3 条未收敛，原因见清单 P2 第 4 项
```

**必须诚实**：没读过的、没跑过的、被截断的、没收敛的，全部写出来。这一段的长度直接反映审计的可信度——写"已完整检查"而实际没读，比不写更糟。

## 反例（不要这样写）

```
❌ 建议对项目进行一轮重构，提取公共模块，补充单元测试，统一代码风格。
```

理由：没有位置、没有动作、没有依据、不是清理。

```
❌ 删除了大量无用代码，提升了代码质量。
```

理由：数量、位置、依据全无，无法复核。

```
❌ 顺手修复了 pagination 的 off-by-one。
```

理由：夹带改动。发现即入清单，不进修复栏。

```
❌ 清理了 AI 生成的冗余代码，代码更规范了。
```

理由：把风格偏好当清理。判据只有一条——它是否还对应真实行为。
