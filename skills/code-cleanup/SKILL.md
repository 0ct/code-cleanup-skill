# 代码卫生清理（Code Cleanup）

## 目的：消除上下文漂移，而不是把代码擦干净

这个 skill 解决的不是审美问题。它解决的是**仓库与"关于仓库的描述"之间的不一致**——代码、注释、文档、指令文件、以及 agent 记忆里的印象，各自讲着不同版本的真相。

一旦不一致，后续每一次改动都会踩在错误的前提上：删掉的模块被"复活"成第二份实现，废弃的写法被下一次生成继续复制，测试断言的是已经不存在的契约。

四种漂移源，对应四种清理动作：

| 漂移源 | 表现 | 清理动作 |
| --- | --- | --- |
| **代码漂移** | 上一轮改到一半的尝试、被放弃的分支、绕开报错的临时补丁留在原处 | 删除死代码与被取代的实现 |
| **记忆漂移** | 上下文压缩后，agent 凭摘要判断"这个函数没人用"，于是在旁边又写一份 | 用引用与调用链重建事实，删掉重复的那份 |
| **指令漂移** | `AGENTS.md`/`README`/注释描述的架构已不存在，下一个 agent 照着它写 | 报告给人确认（这是"复活"的种子，优先级高） |
| **习惯漂移** | 模型或工具链更新后，旧的冗余防御、隐式 `any`、过时 API 继续被复制 | 识别并收敛成当前约定的写法 |

判断标准始终是：**这段代码、这份描述，还对应着仓库现在的真实行为吗？**

产出只有两样：**已修复的清单** 和 **待确认的清单**。没有第三种产出——不写建议书，不做重构方案，不顺手加功能。

## 三条不可谈判的原则

1. **代码是唯一事实源。** 压缩后的记忆、上一轮的总结、注释里的说法一律不可信。判断"这个函数还有人用吗"，只能靠读代码、查引用、跑确定性工具。
2. **行为与接口不变。** 清理不是改进。改动前后，公开 API 签名、返回结构、序列化格式、URL/路由、数据库 schema、配置键名、错误码、日志关键字段必须完全一致。
3. **犹豫即清单。** 任何一个"应该没问题吧"的念头，都是把它放进待确认清单的信号，而不是动手的理由。

## 执行流程

### 阶段 0：建立安全基线（不跳过）

```bash
git -C <repo> status --porcelain
git -C <repo> log -1 --oneline
```

- **工作区有未提交改动** → 这些文件是用户在途的工作，默认不改。若残留确实落在其中，先在报告里点名并等确认。
- **无 git 或 HEAD 为空** → 先做项目外快照（`tar czf /tmp/<name>-backup-$(date +%s).tgz -C <repo> .`），报告里写明路径。没有可回滚的基线，不允许开始改。
- 记录**改动前基线**：能跑就跑 `build` / `test` / `typecheck` / `lint`，留存命令与结果（通过数、失败数、报错摘要）。这是"行为不变"唯一能验证的凭据。跑不起来就记下原因，别假装跑过。
- 判断**能否留在工作区改**：可回滚 + 有验证 → 直接改；否则只产出 patch 文件（见 `references/risk-and-fix-rules.md`）。

### 阶段 1：事实扫描（脚本 + 确定性工具）

先跑本 skill 的扫描器，拿到全量线索：

```bash
python3 <skill>/scripts/repo_scan.py <repo> --md /tmp/scan-before.md --json /tmp/scan-before.json
```

覆盖：临时/备份残留、TODO 与调试输出、注释掉的代码、空文件、重复文件与重复代码块、失效相对引用、疑似无引用文件、依赖漂移（JS/TS/Python/Go/Rust，monorepo 逐包）、环境变量漂移、版本号不一致、硬编码路径与疑似凭据、测试缺口、语言分布。带 git 时会给近 30 天改动过的文件打 `🆕` 标记。

再用**语言自带的确定性工具**交叉验证。工具逐文件看，比模型可靠；但入口点配置错了会把活代码报成死代码，所以：

> **先 dry-run，只采纳能解释清楚的条目。** 永远不要对工具输出直接 `--fix`。

具体工具、命令、各语言已知误报见 `references/tooling.md`。两方结论冲突时以**读代码**为准，并把冲突本身写进报告——冲突点往往就是真正的矛盾。

**扫描器不是结论。** `certain` 只说明"事实可核实"，不说明"该删"。

大项目先收敛范围：`--focus src/` 或调 `--limit`，但报告中必须声明哪些目录没扫。

### 阶段 2：通读与上下文重建

按层读，不许跳层：

1. **指令与约定** — `AGENTS.md`/`CLAUDE.md`/`README`、`Makefile`、`package.json scripts`、`pyproject`、CI 配置、`Dockerfile`、`.env.example`
2. **入口代码** — main/server/cli/index，看它把什么装起来、按什么顺序跑
3. **核心模块** — 承载业务逻辑的部分，逐个读完（不是 grep，是读）
4. **周边** — utils、config、types、tests、scripts、migrations
5. **文档与注释** — 只用来发现"说法与代码不符"，不作为事实来源

读完的判据：能不看文件回答四个问题——入口在哪、主数据流怎么走、对外接口面有哪些、怎么构建和测试。答不上来就继续读，不许提前进入修复。

这一步同时是在**重建被压缩掉的上下文**：读完之后手里应该有一份"当前仓库实际长什么样"的心智模型，而不是上一轮对话的残留印象。两者冲突时，删掉记忆，以代码为准。

项目大到一次读不完：第一遍全量看结构 + 入口 + 公开接口，第二遍深读改动热点与扫描命中的位置；报告里列明未深读范围，不要把没读过的说成"检查过了"。

### 阶段 3：十类审计

逐类过，判据与陷阱见 `references/audit-checklist.md`：

| 类别 | 典型形态 |
| --- | --- |
| 损坏 / 不可达 | 指向已删文件的 import、永久为假的分支、`return` 之后的代码、被同名定义遮蔽的实现 |
| 前后矛盾 | 同一常量/枚举两处定义不同；注释描述的算法与实现不符；默认值与文档相反 |
| 重复 / 过时 | 同一逻辑的 v1/v2 两份实现、复制粘贴后只改了一半、被取代但没删的旧函数 |
| 未使用 | 无引用的导出、只写不读的变量与字段、传了没人用的参数、注册了没用的路由 |
| 低效 | 循环内 I/O、N+1 查询、每次调用重建同构对象、热路径上的同步阻塞 |
| 过期注释/配置/测试 | 注释里是旧参数名、配置项已无消费方、测试断言的是已删除的行为 |
| 临时残留 | 备份文件、debug 输出、临时开关、写死的本地地址、被注释掉的调试代码 |
| 依赖 | 声明未用、用了未声明、同一库多版本、为一行工具函数引入的重型依赖 |
| **无谓抽象 / 过度防御** | 只转发的包装层、单次调用的"框架"、吞掉异常的空 catch、掩盖失败的默认值回退 |
| **指令 / 文档漂移** | `AGENTS.md`/`README`/注释描述的模块、命令、约定已不存在或不成立 |

后两类是 agent 时代的产物，判定手法单列在 `references/agent-residue.md`。

### 阶段 4：分级决策

| 级别 | 含义 | 动作 |
| --- | --- | --- |
| R0 | 纯残留，不在任何运行路径上（备份文件、空文件、已确认无引用的注释代码） | 直接改 |
| R1 | 局部低风险（未使用 import、调试输出、私有符号无引用、注释与实现不符） | 直接改，须通过阶段 6 验证 |
| R2 | 有外部可见性或跨模块影响（删导出符号、合并重复实现、移除依赖、改默认值、删测试、修矛盾、改指令文件） | 只进清单 |
| R3 | 禁改区（鉴权/加密/并发/序列化/迁移、feature flag 内部、生成代码、vendored、凭据、用户未提交改动） | 只进清单，标注"勿自动处理" |

**优先级不是绝对严重度，而是"离漂移源有多近"：**

1. `🆕` 近期改动过的文件里的残留 —— 最可能来自上一轮没收尾的修改
2. 同一语义存在两份实现的 —— 下一次生成会在两处之间随机挑一个，这是污染的放大器
3. 指令文件与代码不符的 —— 它会主动制造新的漂移，属于"种子"
4. 其余按 R 级别与影响面

**自动修改的四个必要条件，缺一不改：**

1. 能证明它不可达或已被取代（引用计数为 0 **且** 不是动态入口：反射、字符串路由、插件扫描、模板引用、CLI 子命令、测试收集都算动态）
2. 不触及公开接口签名、序列化字段、路由、schema、配置键
3. 改动局部、可逆、无连锁（单文件或单函数内，删掉不影响其他调用点）
4. 有验证手段（测试/构建/类型检查），或能静态证明等价

细则与各语言陷阱见 `references/risk-and-fix-rules.md`。

### 阶段 5：最小改动修复

一次一类，改完即验证，不要攒 50 处再一起跑。

**允许的改动**：删除死代码与残留文件、删除无引用 import、删除调试输出、订正与实现不符的注释、删除已无消费方的配置项。

**明确禁止**（这些属于"顺手重构"，不算清理）：

- 重排 import、改缩进/引号/分号/尾逗号、整文件格式化、按 linter 规则批量重写
- 重命名任何标识符、抽取公共函数、拆文件、加类型标注、加抽象层
- 升级/降级依赖版本、替换等价库
- 改错误信息文案、改日志格式、改默认值
- 为了让改动"看起来完整"而新增测试、新增注释、新增文档
- 在代码里留下 `// cleanup`、`// removed xxx` 之类解释性噪音

删掉一个分支、一个 `catch`、一个默认值时，先问：**错误路径是否因此改变？** 会变就降到 R2。

### 阶段 6：验证

按顺序，能跑几步跑几步：

```
语法/编译 → 类型检查 → 改动文件的 lint → 单元测试 → 构建 → 冒烟运行
```

- 与阶段 0 基线对比：**测试总数不得减少，通过数不得下降，类型检查错误数不得增加**。变差就回退那一处。
- 无测试项目：用**行为快照**替代——改动前后各跑一次同一条命令/同一批输入，比对输出与退出码（见 `references/risk-and-fix-rules.md` 的"无测试时的验证"）。
- 跑不了的环节，报告里写"未验证：<原因>"。**没验证的修复只能说"已改待验证"，不能说"已修复"。**

### 阶段 7：输出与复扫

按 `references/report-template.md` 输出：结论 → 已修复 → 待确认清单 → 未覆盖范围。有基线时附**清理效果对比**。

然后**必须再扫一遍**：

```bash
python3 <skill>/scripts/repo_scan.py <repo> --md /tmp/scan-after.md --baseline /tmp/scan-before.json
```

理由有三：删除会制造新的死代码（连锁效应）；清理本身可能引入新的残留；第二遍同类条目仍然大量存在，说明该类判定标准没收敛，要回头修标准而不是继续删。

**收敛判据**：第二遍在已处理类别上应接近 0；若某类数量基本没变，停下来说明原因，不要硬删到达标。

## 清理本身也会制造漂移

删掉一个模块，却把描述它的文档和指令留在原处，下一个 agent 会照着文档把它写回来——这就是"僵尸模式"。所以：

- 删除代码后，**必须**检查引用它的注释、文档、`AGENTS.md`、示例、CI 配置；这些改动属于 R2，写进清单而不是擅自改
- 报告里明确写出"删除 X 后，以下 3 处描述已失效"，把复活的种子点名
- 不要在代码里留 `// 已移除` 之类的墓碑注释，那是新的噪音

## 需要停下来问用户的情况

只有四种：

- 待处理项涉及公开接口或跨模块语义，且删除后无法本地验证
- 需要删除的代码处于 R3 区，但看起来确实是死代码
- 工作区有未提交改动，且清理目标正好落在这些文件里
- 需要修改 `AGENTS.md`/`README` 等指令文件的内容（会影响后续所有 agent 的行为）

其余情况自己判断，不要用"要不要我继续"来替代判断。

## 常见失败模式

| 症状 | 后果 | 纠正 |
| --- | --- | --- |
| 把扫描器/工具输出当结论，批量删 | 删掉动态加载的模块 | `certain` 只代表事实可核实，删除仍需引用证明 |
| 对工具直接 `--fix` | 入口点配错时成片误删 | 先 dry-run，只采纳能解释的条目 |
| 凭压缩前的印象判断"没人用" | 删掉活代码，或写成第二份 | 只信当前代码里的引用与调用链 |
| 把清理做成重构 | diff 巨大、无法 review、引入回归 | 只删不加，不改结构 |
| 把 speculative 当 certain | 清单噪音掩盖真问题 | 置信度如实标注 |
| 删完就收工，不看文档与指令 | 下一个 agent 把删掉的代码复活 | 必查引用它的说明性文字，列入清单 |
| 悄悄扩大范围 | 用户不知道改了什么 | 所有改动必须能在报告里逐条对上 |
| 只给"建议补充测试""建议重构" | 输出无用 | 每条建议必须指向具体位置与具体动作 |
